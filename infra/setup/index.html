3 Accounts & credentials

GitHub — the build & deploy engine not connected

The whole NAS pipeline lives in your repo's Actions: one fine-grained token drives this page live and is stored as IAC_GH_PAT so the bootstrap workflow can manage environments too. Point it at a repo that carries munni — or at a name that doesn't exist yet, and this page forks okkes/munnimok under it. Branches are munni's own (dev/master), picked automatically.

This card only appears because Android/iOS is ticked: the native apps are BUILT by GitHub CI (never on this machine), so those builds need your repo's Actions. Everything else on the local track stays GitHub-free. Same token rules as the NAS track; a nonexistent repo name gets forked from okkes/munnimok.

How to create the token (2 minutes)
  1. Open github.com/settings/personal-access-tokens/new.
  2. Repository access: Only select repositories → your munni repo. (If you want this page to CREATE the repo as a fork, pick All repositories instead — a fine-grained token can't pre-select a repo that doesn't exist yet.)
  3. Repository permissions: Administration Read and write · Secrets Read and write · Variables Read and write · Actions Read and write · Contents Read-only.
  4. Generate, copy the github_pat_… value and paste it below. Set a long expiry — rotating it means redoing only this step.

4 First bootstrap

One workflow run per stack: creates the GitHub Environment, mints every generated secret (postgres password, VAPID pair, GlitchTip key…), renders compose + env and uploads a personalized runbook as the run artifact. Re-running is always safe — it only fills gaps.

5 Deploy to the NAS

The deploy workflow renders each twin from its environment, bundles it and uploads via the FileStation API; the NAS poller (runs every ~5 min) unpacks it into /volume1/docker/<stack>/ and starts the containers. No SSH at any point.

Still manual on the NAS (once) — two DSM clicks

The DSM firewall API is too fragile to automate safely, so bootstrap only PROBES these. Reverse-proxy rules, in contrast, are created by the workflow itself.

  1. Control Panel → Security → Firewall: allow 172.16.0.0/12 (the docker bridge — Logto self-fetches through the host gateway).
  2. Restrict munni-iac-admin.<domain> and logto-iac-admin.<domain> to LAN only.

DNS: with Synology DDNS the *.<domain> wildcard already resolves — nothing to do. External registrars need records for munni-iac.<domain>, munni-iac-test.<domain>, munni-iac-api… etc. (full list in the runbook artifact).

4 Run munni on this machine

Three stacks, one machine: shared services (GlitchTip, the vault, OCR, the munni-control cockpit, pgAdmin) plus TWO complete munni environments — production at localhost:8380 (your real data) and development at localhost:8480 (safe to break). Each environment runs its OWN sign-in service and its OWN database server with its own password — deleting one can never touch the other, and neither holds credentials for the other's data. Nothing is installed on the host beyond Docker Desktop (and node, which this repo already needs).

One double-click and this page does the work itself

You're viewing the file directly, so the page can only guide. Start the local helper and it gains hands: it stores the values you paste, runs bootstrap and docker for you, and streams every step's output right here — no terminal needed.

infra\setup\start.cmd        (double-click it — or: node infra/setup/serve.mjs)
Manual fallback — the exact commands the helper would run
  1. Shared services first: $env:NAS_GHCR_PAT='<read:packages PAT>'; node infra/bootstrap.mjs --stack munni-local-shared then cd infra/rendered/munni-local-shared; docker compose --env-file .env.munni-local-shared -f docker-compose.munni-local-shared.yml up -d
  2. Each environment: node infra/bootstrap.mjs --stack munni-local-prod (same for munni-local-dev) → cd infra/rendered/<stack> → compose up -d. Re-run bootstrap once its Logto answers so the sign-in apps land.
  3. GlitchTip token → $env:IAC_GLITCHTIP_API_TOKEN='…' → re-run the env bootstrap → up -d. Verify: node infra/bootstrap.mjs --stack munni-local-prod --verify
  4. From-source dev loop: docker compose --env-file deploy/env/.env.local -f deploy/docker-compose.local.yml up -d --build + npm run dev (see deploy/README.md).
  5. Tooling: deploy/docker-compose.sonar.yml + ./deploy/sonar/analyze.ps1; deploy/docker-compose.test.yml; ./deploy/webkit-e2e.ps1.

Your secrets & the vault read them back any time

6 Sign-in service (Logto) — the ONE manual auth step

Logto is the self-hosted identity provider the pair owns (accounts, sessions, Google/Apple sign-in). Its very first admin user can't be scripted (no headless OOBE upstream yet) — but it's one visit, and everything after it is code.

  1. Open logto-iac-admin.<domain> → create the admin user (this is YOUR console login, not an app user).
  2. Applications → Create → Machine-to-machine → name it infra → assign the Logto Management API role (all permissions).
  3. Paste the app's id + secret here and store — they land in both iac environments:

After the re-runs, web/admin/native apps + redirect URIs + API resources exist in Logto and their ids are written back to the environments automatically ( VITE_LOGTO_APP_ID appearing = done). Deploy again (step 5) so the frontends pick them up. Google/Apple sign-in from step 3 is wired in the same runs.

9 Native apps

Builds always run in GitHub CI — nothing compiles on this machine. Only the stores' one rule stays manual: the FIRST binary upload of a new app id.

  1. Android: the download lands as a ZIP — unzip it, then Play Console → create the app → Internal testing → upload the .aab → grant the CI service account. Every later upload is CI.
  2. iOS: App Store Connect → New App — the workflow's TestFlight lane takes over from build 2.

Android on your phone (via Play)

Each environment is its own store channel — app id app.munni.local.<env>, delivered through the Play internal testing track, installable side by side. One button: this page writes that environment's LAN config into the GitHub environment local and has CI build + publish it; your phone gets updates from Play like any app. Until the one-time Play setup is done the build SKIPS the upload (no red runs) and hands you the signed bundle instead — and once you finish the upload, this page NOTICES by itself (it polls Play with the service-account credential from step 3) and turns publishing on, nothing to press. The app trusts the family certificate out of the box — CI bakes it into the build, so nothing needs installing on the phone for the app itself. Only for using the phone's BROWSER against the https hostnames: download http://ca.<ip-dashed>.sslip.io → root.crt (mind the DASHES in the address, not dots). Needs the GitHub card in step 3.

The one-time Play setup (once per environment)
  1. Play Console → Create app → package app.munni.local.<env>. Creating the RECORD is the whole manual part — you can do it before any build exists.
  2. This page detects the record within a few minutes (“store app found”) and turns auto-publish on — from then on every build, the FIRST included, uploads itself to Internal testing. Add yourself as a tester there once.
  3. No record yet when a build turns green? The signed .aab downloads here as a fallback for a manual first upload.

iOS on your phone (via TestFlight)

Same per-environment store channel: bundle app.munni.local.<env> (the selector above picks the environment), built by CI and uploaded straight to TestFlight — install and update it from the TestFlight app. One-time first per environment: create the app record in App Store Connect with that bundle id — with the ASC key in step 3 this page checks for the record by itself (pill below). First time on an iPhone: install the family certificate once — download http://ca.<ip-dashed>.sslip.io → root.crt (DASHES in the address, not dots), then ALSO enable it under Settings → General → About → Certificate Trust Settings (iOS offers no in-app trust bundling — Apple's floor). The build carries the LAN address, so it only works on your wifi.

The one-time App Store Connect setup (once per environment)
  1. Nothing to click at developer.apple.com: pressing Build registers the App ID (bundle app.munni.local.<env>) through the API with the capabilities munni needs LONG-RUN — Push Notifications (for FCM later; ticking now means never re-provisioning), Sign in with Apple (Apple requires it beside Google login), Associated Domains (universal links on the hosted track). Apple Pay is NOT needed — munni only reads bank data.
  2. If you ever open the identifier by hand: the “Push Notifications → Configure” dialog offering APNs SSL certificates is the LEGACY path — create nothing there, just Done. Push will use the team APNs key via Firebase.
  3. The one step Apple gives no API for: App Store Connect → New App → pick the pre-registered bundle id from the dropdown → create. The pill above detects the record and every build then uploads to TestFlight by itself.
