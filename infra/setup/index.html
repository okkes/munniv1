    Connection

    The whole NAS pipeline lives in your repo's Actions: one fine-grained token drives this page live and is stored as IAC_GH_PAT so the bootstrap workflow can manage environments too. Point it at a repo that carries munni — or at a name that doesn't exist yet, and this page forks okkes/munnimok under it. Branches are munni's own (dev/master), picked automatically.

    This tile only appears because Android/iOS is ticked: the native apps are BUILT by GitHub CI (never on this machine), so those builds need your repo's Actions. Everything else on the local track stays GitHub-free. Same token rules as the NAS track; a nonexistent repo name gets forked from okkes/munnimok. After a successful Connect the token is saved in this machine's gitignored store like every other credential on this step — the next visit reconnects by itself.

    How to create the token (2 minutes)
    1. Open github.com/settings/personal-access-tokens/new.
    2. Repository access: Only select repositories → your munni repo. (If you want this page to CREATE the repo as a fork, pick All repositories instead — a fine-grained token can't pre-select a repo that doesn't exist yet.)
    3. Repository permissions: Administration Read and write · Secrets Read and write · Variables Read and write · Actions Read and write · Contents Read and write · Workflows Read and write (the last two let this page keep a copy’s pipeline files in step with upstream).
    4. Generate, copy the github_pat_… value and paste it below. Set a long expiry — rotating it means redoing only this step.

    4 First bootstrap

    One workflow run per stack: creates the GitHub Environment, mints every generated secret (postgres password, VAPID pair, GlitchTip key…), renders compose + env and uploads a personalized runbook as the run artifact. Re-running is always safe — it only fills gaps.

    5 Deploy to the NAS

    The deploy workflow renders each twin from its environment, bundles it and uploads via the FileStation API; the NAS poller (runs every ~5 min) unpacks it into /volume1/docker/<stack>/ and starts the containers. No SSH at any point.

    Still manual on the NAS (once) — three DSM screens

    What the two workflows do: Bootstrap (the step above) mints the environments AND writes every reverse-proxy rule through the DSM API — its output line dsm: reverse-proxy apply failed means the deploy account may not use DSM (code 402/119): Control Panel → User & Group → the deploy user → Applications → allow DSM + File Station, administrators group, then run Bootstrap again. Deploy only uploads the bundle; the poller below applies it within five minutes. Certificate: every reverse-proxy host is https, so DSM needs a certificate that covers *.<domain> — the DDNS default covers only <domain> itself (found live: a browser then refuses munni-iac.<domain>). Once: Control Panel → Security → Certificate → Add → Get a certificate from Let’s Encrypt → your DDNS domain WITH the wildcard option → set as default (the rules use the default). Own domain: acme.sh with the synology_dsm hook (docs/iac-plan.md §4). Bootstrap’s Verify names every host the certificate misses. The DSM firewall API is too fragile to automate safely, so bootstrap only PROBES the firewall.

    1. The poller (once per NAS): Control Panel → Task Scheduler → Create → Scheduled Task → User-defined script · user root · daily, repeat every 5 minutes · run: cd /volume1/docker/munni && cp apply.sh .apply.run && sh .apply.run (adjust the share; deploy/nas/README.md). Until it exists, uploaded bundles just sit in the published folder.
    2. Control Panel → Security → Firewall: allow 172.16.0.0/12 (the docker bridge — Logto self-fetches through the host gateway).
    3. Restrict munni-iac-admin.<domain> and logto-iac-admin.<domain> to LAN only.

    DNS: with Synology DDNS the *.<domain> wildcard already resolves — nothing to do. External registrars need records for munni-iac.<domain>, munni-iac-test.<domain>, munni-iac-api… etc. (full list in the runbook artifact).

    4 Start the family

    One machine, one family: shared services (GlitchTip, the vault, OCR, the munni-control cockpit, pgAdmin) plus any number of complete munni environments — production for your real data and, if you like, others to experiment in. Each environment runs its OWN sign-in service and its OWN database server with its own password — deleting one never touches another. Nothing is installed on the host beyond Docker Desktop (and node, which this repo already needs). Addresses: localhost ports until a phone or https feature switches the family to LAN mode (real https hostnames).

    What's left for the family

    Everything this page can do, it does by itself. This list is only what stays yours at the FAMILY level — in order, detected wherever a provider lets us check, a checkbox where it does not. Each environment lists its own steps in its workspace below. “open” jumps to the card with the exact clicks.

      Set up & start everything one button

      One button does the whole family: mints the secrets, starts the shared services, creates the production environment when none exists yet, and brings everything up — waiting for each piece and wiring sign-in, crash tracking, the vault and (when a feature needs the network) the https mode with its certificate automatically: when Windows asks to trust a root certificate mid-setup, that is the family's own — approve it. Saved credentials join in whenever you save them; pressing it again is always safe, it only fills gaps.

      Keeps itself up to date

      The setup above is a ONE-TIME bootstrap. From then on this helper is the PC’s counterpart of the NAS deploy poller: every 10 minutes it fetches this checkout’s branch, fast-forwards when the working tree is clean, re-renders every stack from the machine store after a pull, pulls the newest image of each channel and brings the family up again — restarting itself when its own code moved. Nothing is pushed to this PC; it pulls, exactly like the NAS. Register it at logon and it runs without this page (the store credentials never leave the machine).

      Shared services

      The family's common ground, always running — Set up starts it, Stop/Delete everything are the only ways it goes down. addresses appear once the family is set up — control watches the shared GoCardless account across ALL environments (sign in with your production admin); pgAdmin is one console over every database server (logins under Reveal secrets, servers preregistered).

      Your secrets & the vault read them back any time

      Every generated or saved secret lives readable in this machine's gitignored stores (one per stack, shared values kept once) — and a Vaultwarden vault (the self-hosted Bitwarden server) runs in the shared stack at localhost:8384 as the human copy, usable with the real Bitwarden apps/extension. One button does the whole vault: creates the account with a generated master password (kept in the store, shown under Reveal), imports every sign-in and secret as real vault items, and closes signups. Re-press it any time to re-sync the items after setup changes. The vault is served over https with a locally-minted certificate (the Bitwarden client demands https) — your browser warns ONCE about it; choose Advanced → proceed, it is your own machine signing for itself.

      Manual fallback — your own account instead
      1. Open localhost:8384 → Create account with a master password of your own (needs signups open: save VAULT_SIGNUPS_ALLOWED= empty and press Set up).
      2. Download the import file (button above) → in the vault: Tools → Import data → format Bitwarden (json) → select the file → Import.
      3. Harden: save VAULT_SIGNUPS_ALLOWED=false and press Set up again.
      Developer extras — not needed to run munni

      The from-source dev loop develop against it

      API + Logto + Postgres in docker built from THIS checkout, the app via npm run dev with hot reload (run that in a terminal — hot reload can't live in a container; details in deploy/README.md). This is separate from the registered environments above, which run released images. Verification tooling (SonarQube, e2e, WebKit) stays in the repo's scripts — it belongs to development, not setup.

      5 Environments

      Each environment is a full munni of its own — isolated sign-in, database and addresses. Its workspace holds everything that carries ITS name: the registrations at Google, Apple and Enable Banking, its phones and store records, its admin access. Family-wide things (credentials, shared services, the network mode) stay in the step above.

      Add an environment

      Any number, side by side — each with its own sign-in, its own database server, its own ports. Name it and pick which releases it follows; it spins up and wires itself.

      6 Sign-in service (Logto) — the ONE manual auth step

      Logto is the self-hosted identity provider the pair owns (accounts, sessions, Google/Apple sign-in). Its very first admin user can't be scripted (no headless OOBE upstream yet) — but it's one visit, and everything after it is code.

      1. Open logto-iac-admin.<domain> → create the admin user (this is YOUR console login, not an app user).
      2. Applications → Create → Machine-to-machine → name it infra → assign the Logto Management API role (all permissions).
      3. Paste the app's id + secret here and store — they land in both iac environments:

      After the re-runs, web/admin/native apps + redirect URIs + API resources exist in Logto and their ids are written back to the environments automatically ( VITE_LOGTO_APP_ID appearing = done). Deploy again (the Deploy step) so the frontends pick them up. Google/Apple sign-in from the credentials step is wired in the same runs — the connectors live under fixed ids (google-universal, apple-universal), so the callbacks on the sign-in cards are exact; a connector created earlier under a random id is replaced by the next bootstrap, after which the registration at Google/Apple must carry the fixed-id callback.

      7 Crash reports (GlitchTip)

      Self-hosted error tracking for app, admin and API. One account + one token — the org, the projects and every DSN are code after that.

      1. Open glitchtip-iac.<domain> → register the first account.
      2. Profile → Auth Tokens → create a token → paste:

      The re-run creates org + per-stack projects and writes the DSNs back ( VITE_GLITCHTIP_DSN appearing = done). Deploy again afterwards.

      8 Your admin access

      The admin console and diagnosis endpoints only answer to listed OIDC subject ids. Your sub exists once you've signed into the app for the first time.

      1. Open munni-iac.<domain> and sign up / sign in.
      2. Open logto-iac-admin.<domain> → User management → your user → copy the User ID.

      9 Native apps

      Builds always run in GitHub CI — nothing compiles on this machine. Only the stores' one rule stays manual: the FIRST binary upload of a new app id.

      1. Android: the download lands as a ZIP — unzip it, then Play Console → create the app → Internal testing → upload the .aab → grant the CI service account. Every later upload is CI.
      2. iOS: App Store Connect → New App — the workflow's TestFlight lane takes over from build 2.

      • Re-running any bootstrap is idempotent — it re-applies the stack and re-probes.
      • Generated GitHub secrets are write-only by design; retrieving values: docs/secrets-access-plan.md.
